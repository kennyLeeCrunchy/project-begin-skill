# Agent Workflow

本文件用于记录 Agent 协作中的 plan/state 详细规则。仅当用户明确要求查看协作规则、读取整体方案、读取当前进度，或确实需要创建/更新 `plan.md`、`state.md` 时读取。

# Plan 文件

## 生成规则

只在以下情况创建或更新根目录 `plan.md`：

- 用户提供新的大型 PRD、完整产品需求或新开发阶段；
- 需求会改变完整用户流程或 MVP 范围；
- 需求横跨多个模块、页面或接口，需要重新梳理依赖顺序；
- 需求引入重要架构、数据模型或外部系统变化，使现有 plan 明显失效；
- 用户明确要求创建、重建或更新 `plan.md`。

以下情况不更新 `plan.md`：

- 单个配置项、环境变量或字段调整；
- 小范围功能、局部样式、文案或命名修改；
- 普通 bugfix、重构、文档修正；
- 日常实现细节或不改变整体方案的增量需求。

如果无法确定是否属于大型 PRD，默认不更新 `plan.md`，继续完成当前小需求；不要仅为记录一次局部变化而触碰 plan。

## Plan 文件结构

`plan.md` 必须包含以下三个部分：

1. **模块拆分**：列出该需求涉及的所有模块、页面、接口，并简要说明各自职责。
2. **依赖顺序**：标明哪些需要先做、哪些可以并行、哪些存在前后依赖。
3. **关键风险点**：指出可能踩坑的地方、需要跟其他同学对齐的事项、技术不确定的点。

## 读取规则

- `plan.md` 不自动读取，仅由用户主动要求时读取。
- 用户明确要求读取 `plan.md` 或「看一下整体方案」时，才读取。
- 当用户提供大型 PRD 且当前已有 `plan.md` 时，先提醒用户，由用户决定是否覆盖、重新生成或只读不看。
- 小需求和局部调整不需要读取 plan，也不需要反复提醒 plan 已存在。

## 注意事项

- `plan.md` 是阶段性技术拆解文档，不是变更日志，不需要频繁更新。
- 日常开发进度不写入 plan；用户要求记录进度时使用 `state.md`。
- Agent 无权删除 `plan.md`。需求完成后可以提醒用户手动清理，但不会自行删除。

# State 文件

## 用途

本项目使用根目录 `state.md` 记录开发进度，作为会话间的交接文档。

## State 文件结构

`state.md` 必须包含以下五个部分：

1. **当前任务**：用一至两句话说明正在做什么。
2. **已完成**：已完成的主要事项，每条一句话，重点写结论和方案，不写代码细节。
3. **未完成**：待处理事项及当前阻塞原因（如有）。
4. **关键决策**：记录做过的方案取舍及原因（例如「选 A 而非 B，因为...」），这部分是后续会话理解上下文的关键。
5. **下一步计划**：接下来要做的具体事项，按优先级排列。

## 更新规则

- 当用户明确要求「更新 state.md」时，请重新整理并覆盖写入。
- `state.md` 应反映截止文档更新时的最新状态，采用覆盖重写而非追加。

## 读取规则

- `state.md` 不自动读取，仅由用户主动要求时读取。
- 用户明确要求读取 `state.md` 或「看一下当前进度」时，才读取。

## 注意事项

- 代码细节不写入 `state.md`，保持精炼，总长度控制在 500 字以内。
- 关键决策部分不可省略。
- 如果 `state.md` 和 `plan.md` 内容冲突，以 `state.md` 为准，并提醒用户 plan 可能需要更新。
